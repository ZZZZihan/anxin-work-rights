# 安薪乐业：缺失信息识别与下一步动作基线

2026-10-16，本地实验；未训练、未改线上功能、未部署。关联 [Issue #30](https://github.com/ZZZZihan/anxin-work-rights/issues/30)。

**本轮建议：先改善输出协议和程序状态控制，再决定是否做 LoRA。** DeepSeek 在这批合成情境中表现出的主要问题是协议不一致；本地 Qwen 的错误更多集中于重复追问、问错真正缺失的事实、冲突核实方式和失败状态处理。规则方案在付款归属、全量付款与更正语义上出现实际错误，适合承担确定性的校验与计算，暂不适合单独理解任意自然语言。

这些结果只支持这个窄任务的下一步选择，不能证明企业就绪、真实案件准确率或微调收益。

## 做了什么

整理了 24 条训练候选、12 条开发样本、72 条独立留出测试样本，测试集含 36 个语义/对照组。108 条均为 Agent 编写的合成情境，由另一 Agent 逐条复核；没有真实个人材料，没有复制公开裁判全文，也不是人工专家标注。训练候选以输入/标签分离文件及 `train.sft.jsonl` 保存；24 条只用于审阅格式和行为，不足以支持可信的 32B 微调收益结论。**没有执行 SFT、LoRA、DPO、RL 或任何参数更新**。

本任务只判断：某一明确期间的约定工资总额与归属该期间的全部工资付款是否足够明确。下一步只能是追问、提出 `calculate_wage_gap` 调用，或报告工具失败。允许算术差额为负；不把算术差额直接称为法律上的欠薪。工具调用在评测中做确定性算术回放，没有写入真实案件。

输入是固定会话历史和运行器提供的工具状态，输出是状态字段、下一步动作、问题或工具参数。测试不是交互式多轮任务，也没有测 OCR、检索、法规适用或最终法律建议。

## 数据隔离与运行约定

- 同组及其近邻情境只属于一个 split。测试情境包括跨年日期、确认后的更正、计划打款与实际到账、报销混入、付款归属不明、多个有效来源冲突、零付款及工具失败。金标和类别不进入模型上下文。
- 规则实现者仅被允许读取 train/dev 的四个 JSONL；先在开发集调整并冻结规则，然后运行测试。共享目录没有操作系统级访问隔离，该隔离依据工作分工和记录，不能称为强制盲测沙箱。
- `freeze.json` 在测试前固定 17 项源文件、协议及数据哈希。测试后未改变规则、提示词、金标或主评分器，也没有用测试错误重新请求模型来覆盖结果。
- 三种方法接收相同业务信息。两个模型使用相同系统提示，temperature=0、最多 512 输出 token、关闭 thinking、逐条重置上下文、串行、每题一次调用。都采用提示词要求 JSON，没有启用供应商专用的结构化输出约束；这不是对各模型能力的穷尽优化。
- Qwen 使用已有 `mlx-community/Qwen3-32B-4bit`，revision `bcaaf7f538adf166c1080a2befdb4f6019f66639`，无 adapter。“原模型”在本报告指这个未经本任务微调的 4-bit 模型，不是原始全精度权重。
- DeepSeek 请求及响应模型名均为 `deepseek-v4-pro`，成功测试响应的 fingerprint 均为 `a307abda487cd1b463329ccb945ce396`。供应商别名不是不可变权重版本，未来复跑可能变化。

样本及独立测试集由同一任务作者编写，语言风格和任务定义仍有重合。72 条不是 72 个完全独立业务分布，36 个对照组也不足以支持真实泛化或统计显著优势结论。

## 三类读数分开看

主指标 `decision_contract_correct` 要求输出合同有效，缺失/冲突字段、动作、提问字段和工具参数全部符合金标。评分器允许移除一个完整 Markdown JSON 围栏再判内容，所以主指标不等于原始输出能直接被严格 JSON 接口接受。

开发集暴露出“动作合理但空字段遗漏”的现象后，增加了探索性诊断，并保留主评分不变。该诊断**忽略全部 `missing/conflicts` 状态元数据**，只看已输出的动作、声明的问题字段与参数；它不是“只补空字段后的准确率”。随后由独立 Agent 匿名审阅实际问题文字，判断是否问到了真正未知的事实、是否重复询问已知字段，以及是否把事实冲突变成偏好选择。

| 72 条测试，首次请求为准 | 规则 | Qwen3-32B-4bit | DeepSeek V4 Pro |
|---|---:|---:|---:|
| 原始输出为严格 JSON | 72/72 | 52/72 | 71/72 |
| 输出合同有效 | 72/72 | 70/72 | 33/72 |
| **冻结主指标：协议及字段完全正确** | **55/72，76.4%** | **61/72，84.7%** | **33/72，45.8%** |
| 原始严格 JSON 且主指标通过 | 55/72 | 42/72 | 33/72 |
| 探索性：忽略状态元数据后的动作/声明字段 | 55/72 | 63/72 | 71/72 |
| **探索性：动作/参数与实际提问文字均合适** | **55/72，76.4%** | **62/72，86.1%** | **71/72，98.6%** |
| 两个组内样本均通过业务语义 | 24/36 组 | 27/36 组 | 35/36 组 |
| 在应追问/报告失败的 40 条中提前调用计算 | 5/40 | 0/40 | 0/40 |
| 单请求耗时中位数，不含模型加载 | <1 毫秒 | 6.18 秒 | 2.44 秒 |
| 单请求耗时 P95 | <1 毫秒 | 8.06 秒 | 3.81 秒 |

主指标下 DeepSeek 的低分不能解释成“理解工资问题的能力更差”。其 71 条成功响应的动作/参数与文字复核均通过，但 38 条存在输出协议问题，另有 1 条请求超时。协议问题中，25 条省略 `questions:[]`，9 条虽然提出了必要追问但 `missing` 错误留空，还有遗漏 `tool:null`/`arguments:null` 的情况，类别有重叠。状态自述不一致比遗漏空字段更实质，不能一律无条件补字段后放行。

反过来，不能只看动作字段就把 Qwen 的 63/72 当最终提问质量。匿名文字复核把两条“希望采用哪个金额”的问题判为不充分；同时有一条虽然用了不允许的 `period_end` 标签，文字却准确只问缺失的结束日，业务语义可通过、协议仍失败。综合后为 62/72。

“希望采用哪个金额”与“请确认应以哪个金额为准”的边界属于本次审查解释口径。若宽松接受前者，Qwen 的探索性业务语义读数会变为 64/72（88.9%），不改变主指标，也不改变优先解决重复追问/状态处理的建议。这不是法律专家或真实用户验收。

开发集主指标为规则 12/12、Qwen 10/12、DeepSeek 5/12。规则用过这些开发样本，因此不把开发分数与测试分数合并。没有根据测试结果优化当前提示词或规则。

## 具体问题出在哪

**付款归属与完整性：这是规则方案最明显的业务短板。**

`c_763cdad06820` 的输入是：“2026年8月5日至8月25日，应发合计6300元。8月1日拿过预发1800元，但不确定归7月还是本次；期间收到700元本段工资，除此没有收款。”

- 正确下一步：问清 1800 元是否属于本次期间；已知 700 元不需要再次确认。
- 规则：直接用 `paid=700` 提出计算，跳过了仍不明的预付款归属。
- Qwen：追问已明确的应发 6300 元、700 元是否属于本期，漏掉真正不明的 1800 元。
- DeepSeek：正确问 1800 元的归属，但 `missing` 错误留空，因此业务语义通过、主协议失败。

这个例子说明三类修复不同：规则需理解付款语义，Qwen 需改善追问目标，DeepSeek 需改善结构化状态一致性。

**同一个数字出现在文本中，不代表它就能进入工具参数。**

`c_217a38fc7fa0` 已把“计划打款 3000”纠正为“实际到账 2800，且是完整工资付款”，规则仍使用 3000。`c_cd9ebc965c35` 已确认预发 1800 与另付 700 均属于本期，规则只取 700。`c_e93d9c84dc8e` 两笔完整工资应合计 1700.50，规则只取首笔 800.25。这是 3 个实际数值参数错误，不能与“本该调用却继续追问”混成一个金额错误率。

本来应该调用工具的 32 条中，规则实际正确传参 24 条、错误传参 3 条、另 5 条未调用；Qwen 正确调用 31 条、另 1 条多余追问；DeepSeek 32 条实际参数均正确，但主评分仅 7 条满足完整输出合同。单看 `correct_tool_arguments` 容易把协议错误误读为算错钱。

**追问需要解决事实，不能只凑齐字段标签。**

Qwen 在期间已明确、付款总额已明确时仍重问；在两份有效材料的金额冲突中，有两条问用户“希望采用哪个金额”。更好的目标输出应要求核对来源或确认核实后的金额，允许冲突暂时保留，不能把个人选择当作冲突已经解决。这些是后续可建设的行为样本，而不是背诵法规样本。

**工具重试额度属于程序状态。**

4 条工具失败场景中，Qwen 有 2 条在 `TIMEOUT, attempts=2, max_attempts=2` 后继续追问业务事实，应当报告工具失败。这不等于它实际再次调用了工具；本次未观察到 Qwen 超限调用。实际系统应由程序直接拦住不可执行动作，不依赖微调去学习硬性上限。

本报告列出主要模式；完整逐题输出、主评分、匿名文字复核及映射见 [comparison.json](comparison.json) 和 [results/](results/)。

## 本地资源、API 失败与费用

Qwen 在 Apple M2 Ultra、64 GiB 内存上完成 12 条开发与 72 条测试。测试整段约 475.3 秒，MLX 峰值分配约 17.60 GiB；这是 MLX 分配量，不是全机或进程总内存。采样压力等级全部为 1；测试开始 swap 约 1.984 GiB，观测峰值未超过开始值，结束约 1.945 GiB，没有触发持续压力/超时保护。

运行记录含模型加载时间、MLX/transformers 版本、逐题 token ID、原始文本和内存遥测。84 条输出的 token ID 重新解码均与保存文本一致，均正常 stop，两个本次启动的推理子进程均已退出。权重身份沿用此前完整哈希校验并核对当前文件 stat 指纹，没有在此轮重新读取全部权重做完整哈希。

DeepSeek 测试首次 72 次中有 1 次约 122.47 秒超时，失败仍计入 72 的分母。单独恢复请求约 2.87 秒成功，没有覆盖首次失败，也没有把恢复后结果混回主分数。测试 P95 没有体现这一最慢尾部，超时必须单列。

含 1 次开发预检、12 次开发、72 次测试及 1 次恢复，总计 **86 次尝试、85 次成功响应**；成功响应报告 55,464 tokens。按核查时 [DeepSeek 官方价格](https://api-docs.deepseek.com/quick_start/pricing/) 的峰/谷单价及缓存命中量估算，全部成功请求约 **0.023–0.046 美元**，其中正式测试约 0.019–0.037 美元。未核对真实账单，超时请求是否计费未知；该数不包含本地计算成本，也不能推广为生产平均成本。

## 如何据此决定 LoRA

**当前先不训练。** 更低成本、也更容易解释的下一步实验是：

1. 在开发集上简化冗余输出状态、明确 ask/call/failure 各自需要的字段，加入严格校验；只对确定无歧义的缺省空值做规范化。字段与动作冲突时应拒绝执行或重新核实，不默默改写事实。可进一步比较供应商结构化输出能力，但本轮尚未测试。
2. 把工具重试、时限、权限与可执行状态放到程序控制。模型负责从语境识别未知、冲突和更正，并生成合适的澄清问题。不能靠训练替代确定性限制。
3. 若确实需要本地推理，再围绕 Qwen 暴露的行为补充高质量 SFT 候选：只问真正缺失部分、区分“旧说法已纠正”与“来源仍冲突”、区分付款归属/全量性、冲突核实而非偏好选择。LoRA 的目标是学习这些行为，不是记金额答案。
4. 本次测试集已经被用于分析，后续调优时将它保留为回归集，并另建不参与调优的验收集。应加入授权真实材料或独立作者情境、人工复核、长对话和真实工具失败闭环，再讨论泛化与微调收益。

如果最终主推理仍由 DeepSeek API 完成，这轮没有证明“必须先训练本地 32B 再接 DeepSeek”有收益。本地模型增加部署和维护成本；只有隐私、本地运行、延迟或业务语义效果在新的验收中体现明确价值，才值得把 LoRA 接入生产流程。RL 同样没有必要为了简历标签先行引入，当前先把任务与监督信号做可靠。

## 复核与复现证据

- 数据作者、规则作者、独立复核者分别承担实质任务，3 名子 Agent 请求配置均为 `gpt-6.1-sol / ultra`；工具成功接受配置，不等于独立核验服务端实际模型路由。主任务完成运行、集成与结果核对。
- 独立复核覆盖全部 108 条数据、冻结源码及 145 条匿名实际输出，其中 144 条来自首次测试，1 条为单独恢复。首次测试按后端分别复核规则 44、Qwen 39、DeepSeek 61 条，涵盖所有实际问题和所有主评分失败；剩余 72 条无问题输出由确定性评分核对。没有声称全部 216 条都经人工/Agent 逐条复核。
- 17 项原始冻结哈希保持不变；37 项实验单元检查通过。独立复核在 Python 3.12.12 和本机 Python 3.14.7 上重跑数据/冻结/评分检查，不调用模型。
- 本地 `npm run check` 通过：107 项应用测试及构建/类型检查等通过；材料服务测试 23 项通过，1 项平台相关跳过。隔离的真实 HTTP 文本材料回归通过，覆盖权限隔离、原件保留、人工更正、服务重启与显式恢复等；未连接生产写入。
- GitHub CI 状态以 PR 当前检查为准。CI 新增数据、冻结清单、评分器检查，无凭据，不加载模型、不请求 API、不训练。合并、部署和用户人工验收均不属于本轮完成项。
