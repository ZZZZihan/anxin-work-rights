# 安薪乐业 v2：协议与工具控制的配对实验

日期：2026-10-16。没有训练、LoRA、适配器或权重更新。

本轮完成的是离线“缺失信息识别与下一步动作”组件及真实本地算术分发，未接入网站 `/api/chat`，未合并或部署。四臂均使用相同 72 条新留出样本；旧 v1 代码、数据和结果保持原样。模型版本为本机 `mlx-community/Qwen3-32B-4bit`（固定 revision 与文件校验）及 DeepSeek API `deepseek-v4-pro`（返回别名记录，不能像本地权重一样完全固定服务版本）。

## 已完成的工程改动

模型输出只保留两种有明确结构的动作：`ask_user` 和 `call_tool`。追问带字段、原因和实际问句，计算带允许的工具名及参数；程序从它们生成规范记录，不要求模型重复写多套一致的状态数组和空字段。仅可移除整个响应的 JSON 围栏并留痕，不自动修金额、猜字段或用另一个模型重写。

调用前由程序检查可信工具状态；两次尝试耗尽时不再请求模型。次数在执行前记账，业务对话里的“重置次数”不改变程序状态。单个控制器内并发重复不会再次执行；成功同参调用复用结果，改变参数拒绝。实际工资差额使用 Decimal，且验证工具返回的金额和期间；失败不冒充成功。

这些保证不包含自然语言事实校验、持久化会话、跨进程幂等或任意阻塞工具的强制超时取消。当前合法参数仍可能没有事实依据，下面保留了真实触发的模型失败。

## 数据与评测边界

新集为 72 条 Agent 合成对话、36 个二元对照组，含 16 条多轮快照；30 条应调用工具，34 条应追问，8 条应终止。不是实际投诉记录、法律专家标注或真实用户完成率。

样本作者只读原业务合同，不读旧测试、旧结果或 v2 提示词；另一位 Agent 全量审查 72 条标签。实现者先用旧 12 条 dev 验证，再封存 27 个源码/协议文档及 6 个数据文件，之后才开始新集推理。详情见 [开发记录](DEVELOPMENT.md)、[数据说明](data/AUTHORING.md)、[冻结指标](METRICS.md)。共享文件系统下的职责隔离不等于外部团队独立实验。

两版同温度 0、关闭 thinking、输出最多 512 token、逐条重置上下文、无自动重试、无供应商强制 JSON 解码。v2 提示词更长。比较的是提示词、协议和程序控制的组合，不单独归因某个组件。失败留在计划分母，首次结果没有被恢复调用覆盖。

## 冻结规范决策分数

规范决策正确要求：动作、缺失/冲突类别、问题字段、实际工具参数全匹配；v2 还必须具有真实分发状态、精确结果和合法次数凭据。此表尚不以字段匹配代替实际问句语义评价。

| 模型与流程 | 全部 72 条 | 相同 64 条非耗尽样本 | 8 条耗尽样本 | 原始 JSON / 实际模型请求 | 协议接受 / 实际模型请求 |
|---|---:|---:|---:|---:|---:|
| Qwen v1 | 62/72 | 59/64 | 3/8 | 59/72 | 69/72 |
| Qwen v2 | 67/72 | 59/64 | 8/8，程序处理 | 64/64 | 64/64 |
| DeepSeek v1 | 36/72 | 35/64 | 1/8 | 72/72 | 39/72 |
| DeepSeek v2 | 68/72 | 60/64 | 8/8，程序处理 | 63/64 | 63/64 |

v2 每个模型只发起 64 次请求，另 8 条直接由程序终止，不能算模型答对。DeepSeek v2 一次请求失败（记录为 `URLError`）同时保留在非耗尽 64 条与全量 72 条分母；63 个成功响应均为有效协议。没有把网络失败说成 JSON 格式错误。

v1 的离线算术复演本来就有次数耗尽拦截，因此旧模型提出多余调用不等于工具真的越过上限执行。v2 的新增收益是把检查前移到模型请求之前、由程序形成终止输出，并提供实际分发和会话内状态保证。

Qwen 的全量规范分数增加 5 条，净增恰好来自程序处理终态；在相同 64 条上没有净提升。这不能表述为 Qwen 的业务判断能力已经提高。DeepSeek 的旧流程在非耗尽 64 条上动作、字段及参数诊断本已全对，主要损失在输出协议；新流程仍有 3 条原因标签误分类和 1 次请求失败。

逐题配对的规范分数：Qwen 全 72 条新胜 8、旧胜 3、平 61；非耗尽 64 条新胜 3、旧胜 3、平 58。DeepSeek 全 72 条新胜 32、旧胜 0、平 40；非耗尽 64 条新胜 25、旧胜 0、平 39。这个小型配对集不支持统计显著或广泛泛化优越性声明。

## 独立实际问句复核

四臂完成后统一打乱为一个 168 条匿名审查包，覆盖所有金标追问、实际追问及规范失败。审查者不读模型身份映射和带身份的原始结果，审查实际问句是否指向未决事实、是否重复询问已知信息、是否以偏好代替事实核实；参数和字段仍须匹配。风格可能透露身份，所以不称严格实验室双盲。其余无需追问且规范正确的输出由冻结确定性评分器核验。

168 条已全部完成独立 Agent 复核，评分已锁定后才关联身份。审查者先前参与过金标核验，审查包也包含金标，因此这是隐藏模型/版本标识的审查，不是金标盲审或人工专家验收。严格文字口径包括不重复已明确的核实状态；此类边界项具有审查者判断成分，原文与逐条理由全部保留。追问与原因标签的后续改进记录在 [Issue #34](https://github.com/ZZZZihan/anxin-work-rights/issues/34)。

| 模型与流程 | 规范且问句合格：全部 72 条 | 规范且问句合格：非耗尽 64 条 | 业务动作与问句合格：非耗尽 64 条 |
|---|---:|---:|---:|
| Qwen v1 | 58/72 | 55/64 | 56/64 |
| Qwen v2 | 62/72 | 54/64 | 54/64 |
| DeepSeek v1 | 35/72 | 34/64 | 63/64 |
| DeepSeek v2 | 67/72 | 59/64 | 62/64 |

前两列要求冻结规范决策正确，且业务动作审查通过、问句审查不为 false；最后一列不要求旧格式和原因 metadata 合格，用于把业务语义与协议兼容性分开。它们是本轮受限任务的指标，不是完整用户任务完成率。64 条分母均保留请求失败；8 条 v2 程序终止仍只计系统收益。

加入文字审查后，Qwen 在非耗尽样本从 55/64 变为 54/64，逐题新胜 6、旧胜 7、平 51，不能声称改善。DeepSeek 从 34/64 变为 59/64，新胜 25、旧胜 0、平 39；其业务动作与文字诊断从 63/64 变为 62/64，配对为新胜 1、旧胜 2，包含一次请求失败，仍不构成业务能力提升证据。主要收益继续是协议能被程序可靠消费。

Qwen v2 另有 5 条字段/参数正确却实际问句不合格：两条把有效来源冲突变成“您希望/认为用哪个金额”，一条用户已说未核实却重复问是否已核实，一条只索取大概日期，一条把跨期付款限定为全属本期或全属上期，遗漏拆分可能。DeepSeek v2 另有 1 条文字项未过：用户已明确现金、微信未查，模型仍问“是否已查全”，虽同时索取总额，独立审查按“不重复已知状态”的严格口径判错；这应与错误金额调用区分严重程度。

完整四臂指标、分组配对和资源统计见 [comparison.json](comparison.json)；[匿名包](review/blind-batch1.jsonl)及[逐条审查](review/semantic-batch1.json)可供人工复核。没有为提升分数修改审查或补跑失败请求。

## 当前尚未解决的问题

**Qwen：5 条规范错误。** 两条在同时缺少期间与应付总额时只追问期间；一条问的是付款归属金额，却把字段标成 `period`；一条重复要求确认已经核定的应付总额；另有一条把未知应付总额填成 0 并计算。前两条是相对本轮“一次列齐未决字段”合同的完整性失败，并未测试分多轮依次追问是否可补救。

最重要的失败是 `445b5283-6de3-584d-b75c-832f60f4a82c`：用户明确核算范围为 2026-04-01 至 2026-04-23，月薪 5900 元，但整段应付总额未核定，全部已付工资 4500 元。Qwen v2 提出 `due=0, paid=4500`。这些参数通过结构校验，真实工具返回 `gap=-4500.00`，但正确动作应为追问整段确认的应付总额。负差额本身允许；失败在于把未知值当成零。已建立 [Issue #33：计算前核对事实依据](https://github.com/ZZZZihan/anxin-work-rights/issues/33)。

同题 Qwen v1 会追问应付总额，但多问了已知期间，所以也被规范评分判错。v2 把这条变成了错误计算；两个版本都得 0 分不代表风险相同。后续必须单列无事实依据的工具调用，不能只追求平均正确率。

**DeepSeek：3 条原因分类错误，另 1 次网络请求失败。** 三条都把“付款组成或归属尚不明确”标为 `conflict`，金标为 `missing`；实际所问的未决事实正确。例如 2400 元付款包含工资和退还工服押金，但各自数额未知，应该核实工资部分，而不是把它记为两个互相矛盾的已确认值。原因分类是否有业务用途，应在产品中确认，不能为追逐这类标签分数直接安排训练。

## 时延、资源与成本

| 流程 | 实际模型请求 | 模型调用中位时延 | MLX 每次推理分配器峰值最大值 |
|---|---:|---:|---:|
| Qwen v1 | 72 | 6.43 秒 | 17.65 GiB |
| Qwen v2 | 64 | 7.30 秒 | 17.71 GiB |
| DeepSeek v1 | 72 | 2.72 秒 | 不适用 |
| DeepSeek v2 | 64 | 2.38 秒 | 不适用 |

时延不含本地模型加载，也不把 8 条程序旁路的零时延混入。Qwen 在 M2 Ultra 64 GiB 上两臂均完整结束，采样内存压力最高为正常等级 1，交换空间相对各自启动前未增长；MLX 分配器峰值不是全机内存或进程 RSS。DeepSeek v2 的失败请求计入时延分布，网络与供应商状态有波动，单轮结果不能证明长期速度差。DeepSeek 总模型请求时长为 v1 203.43 秒、v2 277.09 秒，其中失败请求约 120.00 秒；较低中位数没有让本批总请求时间减少。

两臂测试中有 usage 的 DeepSeek 响应共 135 次；按当日官方价格估算合计约 0.0356—0.0713 美元，未核对账单，不包含旧 dev 运行，失败请求是否收费未知。价格区间采用官方低峰/高峰费率；更长 v2 提示并不必然增加总费用，实际调用数、输出长度和缓存也会影响。[官方模型价格](https://api-docs.deepseek.com/quick_start/pricing/)

## 下一步决策

继续保持不训练。首先解决可验证的业务事实约束：给期间、应付总额和已付总额记录确认状态与原文出处，严格区分 unknown 和 explicit zero；模型参数必须与可信事实表匹配后才允许计算。不能只信模型自报的来源 ID。再针对多字段遗漏、字段与问句不一致以及已知事实重复确认做新开发样本和新的留出评测。冲突应引导核对来源，不能让用户按偏好选数；跨期款项必须允许拆分。

仅这一小批合成样本不足以决定 LoRA 或 RL。DeepSeek 的主要协议损失已能用工程方法改善；Qwen 还存在会直接影响业务操作的错误，不能因为 JSON 合法率提升就把它当成可自动处理真实案件的模型。
