# v3 初始独立设计审查

审查日期：2026-10-17。范围：可信事实记录、计算前核对、离线组件比较和验收口径。未实现代码，未读取任何 v3 新留出内容或标签，未调用 API、模型或训练，未执行 Git 操作。依据为当前项目 `AGENTS.md`、v2 `CONTROL.md`、`DESIGN.md`、`METRICS.md` 及公开开发失败 `445b5283-6de3-584d-b75c-832f60f4a82c`。

结论：方案方向正确，但只有把“谁能确认事实”和“提案如何绑定当前事实”同时收紧，才能防止将未知金额当作 0。模型自报 confirmed、来源编号、JSON 合法或与候选文本相符，均不能成为可信确认依据。这个阶段可以证明带模拟可信确认输入的组件行为，不能证明真实自然语言抽取、用户确认有效性或生产可靠性。

## 必须先固定的边界

- 自然语言抽取只产生候选；可信确认通过程序掌握的独立结构化渠道进入。不得从 user/assistant 文本、模型 JSON、候选中的 authority/source_id/confirmed 字段自动升级权限。来源存在与来源有权确认是两个条件。
- 离线输入中的可信确认事件是人为构造的组件输入。需要公开承认：离线 Python 调用方被假定可信；允许任意调用方传入一个自称可信的普通对象，不等于已完成生产认证、授权或抗伪造。
- 事件应有稳定身份、受控类型、所属事实/期间、顺序或版本、明确确认者类别；由程序验证其引用是否存在、可用于当前期间以及是否允许此类确认。仅引用一个任意来源编号不足够。
- 三项可执行事实为明确期间、该期间确认应付总额、该期间全部工资付款总额。付款金额和付款清单完整性必须分别表达；月薪、候选总额或部分流水不能被默认为期间总额/全部已付。
- missing/unknown 不使用数值 0 表达。明确确认的 0 是有效金额；due、paid 非负，但 due-paid 可负，不能用禁止负差额掩盖原缺陷。

## 可检查的验收条件

1. **构建只取受控事件。** 事实快照由确定性程序构建，执行路径不读 gold、category、rationale、expected action 或按 case_id 编写的映射；不调用第二个模型补事实。非法事件或引用失败应给出明确错误，不悄悄忽略而产生可执行快照。
2. **状态足以区分语义。** missing、candidate、confirmed、conflict 及明确撤销/纠正具有确定处理顺序；未解决冲突不能靠“最后出现的值”或“更喜欢的来源”消失。明确纠正旧确认与新增相互矛盾来源须区分。
3. **期间与付款完整性绑定。** 确认金额与其期间绑定；修改期间、撤销确认或出现未解决冲突后，旧确认不能继续授权执行。完整性应对应同一期间与同一确认版本。
4. **每次 dispatch 都核对。** 通过结构解析后仍须检查当前可信快照可执行，且 period_start、period_end、due、paid 与当前确认值精确相等。缺事实、参数不符、未知/过期快照均不得调用实际工具，也不得消耗工具尝试次数。
5. **核对与调用之间无空隙。** 快照版本、控制器绑定参数与实际执行参数一致；并发变更/确认撤销不能在检查后绕过。记录实际使用的快照版本，避免只审计最新快照。
6. **合法计算必须成功。** 三项完整且无冲突、参数匹配时应真实调用 Decimal 算术；明确 0、paid 大于 due 的合法算术差均放行。拒绝不能被算成这类样本正确。
7. **原有控制不退化。** 解析拒绝、两次尝试上限、取消/异常留痕、显式重试、同参数成功复用、参数变更拒绝、并发保护继续成立。事实修订不得自动新建控制器来重置既有尝试预算；若需要新操作，须显式记录边界和策略。
8. **分开记录三层结果。** 保留模型原 proposal、gate 原因/所用快照、最终 dispatch/真实结果。程序补问或阻断带来的正确性计为系统控制，不能改写原模型 proposal 后计为模型推理正确。
9. **独立错误口径。** 事实不齐、参数不符、无效可信输入、协议错误、工具超时/错误分别留痕；无事实支持的调用被挡住不等于工具成功，也不等于模型正确。

## 防 oracle 与防拒绝刷分

模型、控制器和实际执行入口只接收白名单输入文件；标签必须在保存不可变运行输出后才由独立评分过程加载。单测可以人工指定期待结果，但不能把单测期待值作为运行时事实。

建议做一项明确的防泄漏验证：保持输入和 proposal 不变，移走/改写标签、category、rationale 与评分文件后重新执行离线组件，输出及调用计数必须完全不变。保存执行读取的文件清单与源码/输入哈希。不要让运行器为“方便”把 labels 读入后再只传其中部分字段。

用固定分母同时报告：

- 未确认/冲突事实下的不当调用阻断数和漏放数；
- 事实充分且 proposal 参数正确时的真实执行成功数、错误阻断数；
- 事实充分但 proposal 参数错误时的拒绝数；
- 模型原始动作正确数、系统最终动作正确数、必要追问正确数和重问已知事实数；
- 同组安全阻断与合法放行同时正确的组数。

全拒绝只能提高第一项，必须在合法执行率和成组指标上失败。分母不能只包含 gate 已接受样本；协议错误、请求失败、缺失结果和过度追问均保留在原计划分母内。按事实状态单列结果，防止通过增加未知/冲突样本稀释合法执行失败。

## 同 proposal 的 gate/no-gate 比较是否足够

足以回答一个窄问题：**面对同一份冻结提案、同一事实输入和同一工具状态，gate 是否减少无事实支持的实际执行，同时保留合法执行。** 两臂必须用独立同初态控制器复演，不能先运行一臂污染另一臂的次数/成功缓存。两臂间唯一差别是 gate；其余解析器、工具、状态、时间限制、输入均保持一致。

不足以证明模型变聪明、自然语言候选提取正确、可信确认流程易用或端到端 Agent 改善。所有模型看到同一可信事实表示后，模型实验只能比较在这些结构化事实下提出下一步的能力。若 gate 根据快照生成正确补问，收益应明确归为程序接管。

本轮建议保留两条互补证据：一条是独立编写的确定性组件回归（可覆盖模型本轮没有提出的无依据调用）；另一条是模型冻结 proposal 的双臂复演。若真实 proposal 中没有危险调用，不能把“零危险执行”解释为 gate 已受实际挑战，应报告组件回归的覆盖。需要做自然语言端到端声明时，另建独立候选抽取/真实确认评测；本轮无须因此扩大范围或启动训练。

## 后续独立复核安排

先审实现与接口契约，再由独立作者交付新集并审标签。冻结前不向实现者传播新集的具体题文、数值、标签或失败分布。实现冻结后如发现标签错误，应留下原标签、修改原因和影响范围；如果实现依据新集失败改变，应建立新一轮留出集，不能继续声称当前集未参与开发。
