# 哪些先改流程，哪些才是 LoRA 候选

以下只分析冻结协议下的原始回答，不修改原回答、提示、金标、接受备选或正式分数。候选索引为零起始。公开行政文书节选与逐块原文见旧 `data/holdout.inputs.jsonl`；这里描述的是材料提取，不是个案法律意见。

## 先改输出与事实流程

1. **JSON 外的 Markdown 围栏**。DeepSeek 九份中三份有围栏；Qwen 九份全部有围栏，其中 `mf4-hn-zf-2021-28` 正文另有非法 JSON 转义，去围栏也不能解析。按原协议整份拒绝，这是可消费格式的失败。预登记的围栏剥除只用于辅助诊断，不将诊断成绩冒充正式成绩。后续优先验证供应端结构化输出或严格、有限且留存原文的格式适配；不应为去掉三个反引号先做 LoRA。
2. **候选上限和重复**。DeepSeek `mf4-yy-2025-8` 输出 42 项，超过 40 项协议上限，整份失败；该份金标只有 22 项。先确定每个事件/实体的输出粒度、别名归并和分块合并规则。不能只抬高上限来改善已看到的分数，也不能无限截取前 40 项。
3. **数值表示合同不完整**。`mf4-yc-th-2024-100` 的 DeepSeek `candidates[3]` 提取 `monthly_rate=3000元/月`，原文有此表达；金标是 `3000元`，当前 `parseAmount('3000元/月')` 返回 null，basic 也不匹配。这不证明模型不会识别该月薪。应把金额与计价周期结构化、完善限定范围内的归一化，另用新样本验证；本轮不追改金标。
4. **时间粒度与断言标注需先定清**。上述文书 `candidates[2]` 合并完整入离职区间，金标拆成两个日期，一对一匹配无法让一个区间覆盖两个日期。此外劳动者“确认”与公司后文“认可”如何合并，claimed/admitted 的粒度要事先定义。不能把全部这类 strict 不匹配直接变成训练负例。
5. **候选只能提出可能事实**。单笔支付、群体总额、不明期间、来源冲突和未知金额都不能自动取得计算资格。继续由可信事实记录和用户确认控制；未知保持 null，只有明确核实的零才可计算。模型分数提高也不取消这道门。

## 后续决策

当前不启动 LoRA/RL。下一步先做一轮小范围的非训练流程改进：明确结构化输出、归一化和实体/事件表示、保证完整性和用户确认门禁，再用新的、按案件分组的独立材料验证。已经揭晓的九份可以留作开发回归，不能继续称为未来训练的独立盲测。

若新样本上仍反复出现，优先考虑 LoRA 学习四类有清晰监督的提取任务：欠付/完整应付/部分支付的区分；劳动者/代理人/企业/班组角色关系；签约/履行/劳动/工资日期角色；引述主张、承认与机关认定的嵌套关系。训练产物只应改善候选提取，不能替代事实确认和计算授权。本轮未做训练，因此没有证据说明 LoRA 一定优于上述流程改进。
