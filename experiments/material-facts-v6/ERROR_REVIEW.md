## 可以直接确认的残余问题

1. **明确有内容却全空。** 鞋业案原文列出 59.6 万、51.5 万、111.1 万及 105.7 万的资产/发薪两个事件；DeepSeek 首次回答为 `{"schemaVersion":3,"candidates":[]}`，5 个参考事实全部缺失。其 JSON 和协议都有效，没有传输或 length 解释。覆盖提示为 empty，能把结果引到原文核对，但没有补回事实，不能称遗漏已解决。规则在全部 8 案均为空，说明这一窄规则基线不能完成本组公开叙述材料的提取任务。

2. **把没有金额的工资描述作为 money。** 王某与投资公司案没有具体工资数额，DeepSeek 却把“2020年12月基本工资”“2019年11月至2020年12月的其他工资”等列为 arrears/award 的 money.value。7 个这类原始候选中 1 个因引用不连续拒收，另 6 个通过字面和条件字段校验，但没有可用规范金额。这是 kind/value 的实质错误，不能因为保留了原文就算正确金额提取。其中诉请本身还被标成 award。需要的日期期间及并列区间因而发生遗漏。现有字面验证没有承诺校验这类语义，58 条“接受”不能读成 58 条可信事实。

3. **把命令发生日期当作付款日期。** 任某案“同月29日，……责令……足额支付工资”描述行政命令发生日，不是实际付款日或明确给付截止日。模型输出 payment_date 并以任某为个人主体，既混淆事件角色，也用了承担支付义务者，而非工资受益群体。类似行政责令发生日还出现在翁某、旅游公司案。投诉、张贴指令、移送、公诉等纯程序日期在多个案件被额外输出，与预先明确的任务范围不符。应将这类问题与明确日历支付截止日的正确提取分开。

4. **用途未等于实际收款。** 旅游公司案“缴纳5万元用于支付拖欠的劳动报酬”没有明确劳动者实际领款，模型却输出 payment/partial，主体为 9 名劳动者。原文后来另述家属足额清偿而没有金额，不能倒推这 5 万已经支付到人。该错误没有触发预登记的 payment_as_paid_total，因为模型没有把它写成 paid_total；focus 计数为 0 不代表所有支付角色正确。

5. **资金转出人被写成收取人。** 张某某案“将近500万元劳务费出借他人”中，模型把张某某作为该笔出借款享有/收取方，而输入没有确定借款收取人的连续名称。这个主体问题是真实的，但官方 basic 先因 value 多带“劳务费”未匹配，不能把它包装成 basic→relational 的主体损失。与之相邻的“截至2025年7月”被截成“2025年7月”，确实丢失了截止边界。

6. **明确上下文的 assertion 没有稳定继承。** 任某案“另查明”后的支付截止日被标 narrated；康某某案“本委经审理查明”中的 4 次签约、离职和结清证明签署共 6 条被标 narrated；投资公司明确承诺欠款及付款截止的 4 条被标 claimed，而冻结约定为 admitted。前两类有清楚的上下文引导，属于模型未保持段落陈述层级。第三类还涉及“历史自认、诉讼中后来否认”的叙述层级，必须按本轮约定解读，不能把 assertion 差异直接解释成法律实体结论错误。

7. **有工资归属 period，独立日期仍缺失。** 康某某未休年假工资输出带 period=2025年，却没有相应的独立 wage_period 日期；投资公司案的诉请和判令并列期间也没有按约定作为独立日期保留。这与日期和金额期间同时表示的任务要求不一致，但其中同事实不同 assertion 的粒度仍受本轮标注约定影响。

## 必须单列的解析、跨度及任务边界

这些仍按冻结评分保留 FP/FN，既不补备选，也不回算一套“改善后”正式分数。

- **人民币前缀。** 冯某案模型取“人民币六万元”“人民币四万元”“人民币四十二万余元”，标签取去掉“人民币”的最小金额。普通小写中文金额当前未规范成可比较的精确/概数语义，规范函数保留 raw，3 个同义金额因而不能匹配。尤其罚金 subject=null、scope=unknown、assertion=decided 已正确，不能把这 3 项低 basic 归为金额理解或主体错误。首先应在未来轮修解析/表示等价规则，并用新样本重新冻结。
- **概数后的名词。** 张某某案“约115万元工资”保留概数、对象、paid_total 和 complete，区别只是 value 比标签“约115万元”多了“工资”；官方 basic 不匹配，但模型已经区分完整累计、群体和概数。不能将此 FP/FN 报成“把未知当零”“误把部分付款当完整付款”。“近500万元劳务费”也存在同样 value 跨度差，但它另有上文所述的收取方错误，两层原因要分开。
- **群体名称及纯连接跨度。** 翁某案“洪某等3人”与标签“工人洪某等3人”明显同指，模型仍用 group，没有把群体当个人；“2020年9月至2021年2月”与“自2020年9月至2021年2月间”也保留同一起止年月。由于本轮未预登记这些有限同义跨度，金额 period、日期 value 和支付日 subject 均按严格字面规则产生损失。这首先是接受备选和边界定义不足，不能直接作为主体混淆训练样本。
- **欠薪快照与工资覆盖期。** 任某“截至2022年1月”标签为 other_date，模型为 wage_period。前者表示余额观察截止点，后者可能被模型理解为开放工资覆盖期。冻结分数仍判错，但应在后续说明中给出“余额时点≠工资归属范围”的明确例子，再要求不同标注者一致判断。
- **工程时间与劳动者任职。** 张某某材料叙述“2022年到2023年底……组织农民工进场施工，2023年底施工结束”，模型生成 2 条 employment_period。标签只将其视为承包/工程时段，没有将它推定为每位劳动者任职。该排除有保守理由，但“施工结束”与群体工作结束之间有合理解释空间；这是任务范围和主体时段的边界，不能简单列成明显胡编。未来应在提示及标注示例中明示工期能否代表群体任职、需要什么直接表述。
- **与争议相关的非工资金额和日期范围并不对称。** 翁某 50 万元售房价作为相关 other_money 进入标签，而售房日被排除，模型却提日期、漏金额。漏金额按本轮规则明确；日期是否一律任务外，需把“相关款项可提、与工资计算无直接关系的财产处置日期不提”写得更具体，不能仅把所有额外日期都当一种语义失败。
- **年假工资类型。** 康某某的已承认年假工资，标签用 due_total/partial，模型用 other_money、保留正确主体、年度和 admitted；它没有把这项当全年完整应付。该类型边界值得专家确认和与补偿类 other_money 的统一，现阶段不宜作为无争议的 LoRA 硬目标。之后的裁判 award 金额则已匹配。

## 诊断与产品集成能证明什么

DeepSeek 接受的 24 个 money 中，完整引文规范状态为 exact 6、unsupported 16、approximate 2；没有将未支持或概数转换成精确 0。部分“万余元”等概数目前得到 unsupported，虽不会生成假精确值，但状态名称和支持范围仍有限，不能把 unsupported 全部解释成非金额。reviewIssues 共 0，说明当前窄词法诊断没有覆盖上述大多数语义错误，不说明无需人工核对。

覆盖状态为 possible_missing 5 案、no_signal 2 案、empty 1 案。冯某和张某某为 no_signal，但仍有前缀/跨度、额外日期或收取方问题，证明 no_signal 只是没有额外启发式线索，不是语义完整或正确证明。鞋业全空是明确的用户提示价值样本，同时仍保留 5 个 FN。预登记 focus 无明确 group_as_individual、payment_as_paid_total、partial_as_complete_paid、signing_as_work_or_performance 计数；同日多角色的歧义配对单列，不强行造错。不能以这些聚焦错误为零宣称总体语义已可靠。

审查者只读核对服务、持久化和界面的最终连接：fact-jobs 与 store 使用 v3，API 只回来源摘要时界面读取已持久化 coverage；显示原文与规范片段、原始回答、拒绝理由和空/全拒收提示；日期不再显示为金额归属 period。新的提取会清空旧确认和计算，非正常结束输出走失败原答复查，模型输出不能写入人工确认。exact 只使金额有可用规范值，候选角色、个人范围、期间、完整性及显式人工确认仍分别受约束；本组语义错误没有因“规范化成功”自动取得计算授权。

主实现报告的完整 check 299 测试、HTTP 10 项和真实浏览器空提取/受控金额/第三人/长引用/全拒收检查，与本审查者的静态集成复核和独立评分复算分开记录。审查者没有重复执行一套浏览器验收，也没有将受控输出说成真实模型表现。当前未发现新的集成阻塞，但完整结果 manifest 及 Qwen 身份/内存事件链仍待最终运行后核验。

## 对后续 LoRA 的界限

本轮不训练，也不能从 v5/v6 不同数据和规则的 F1 差值推出模型提升。当前优先处理的是下一轮的解析/同义跨度规则，以及工程时段、欠薪快照、非工资财产日期和年假工资类型的标注澄清；这些不应作为模型训练错误硬塞进监督数据。

值得继续收集独立案件并在专家复核后考虑的语义方向是：实际收款与“缴入/用于清偿”的区别、付款义务人和收取方区分、行政命令发生日与支付日/截止日区分，以及明确查明上下文的 assertion 继承。它们在多个不同案件出现，有具体业务后果或稳定任务含义。没有金额却输出 money、明确工资事实全空也应保留为失败样本；前者先评估能否由更简单的确定性约束识别，后者当前只有一个 DeepSeek 新案，尚不足以声称是跨案稳定模型缺陷。

在 parser/标注争议排除之后，仍需更多全新案件、独立复核和冻结比较，才能判断是否值得 LoRA。不能把 43 个 accepted strict FP、35 个 FN、11 个 assertion 分差、程序拒收或空提取提示合并成“43/35 个值得训练的法律语义错误”。Qwen 尚待运行，当前也不具备两模型残差对照结论。

## 冻结后另行发现的生产链路问题（Issue #41）

本节追加于读取 PR #40 旧自动审阅后，修正前文“当前未发现新的集成阻塞”的时间边界。以下是审查者用合成材料和当前代码实际复现的工程问题，不是本轮正式留出材料新增标签，也不改变上文评分。

**P1：模型自行裁短 quote，仍可隐去原文的关键限制。** 审查者直接调用冻结 v3 验证、入库状态函数及视图函数，原始 block 为“合成单位：2026年1月，王甲班组10人完整应付工资80000元。”，候选却填 subject=王甲、scope=individual、due_total/complete，quote 只取“完整应付工资80000元”。验证实际接受 1 条、无拒绝、amount=80000.00、reviewIssues=[]；确认个人和月份范围后，应付字段给出 80000.00 候选。把 quote 换为包含“王甲班组10人”的完整事件时，同一实现才会给 scope_text_mismatch 并停止个人金额提示。没有人工金额确认时 canCalculate 仍为 false，故复现证明错误候选和审核提示失真，不能写成系统已自动计算或付款。

同一信任边界还影响金额规范化。将原始 block 分别改为工资“约80000元”“至少80000元”“负 80000元”，模型的 value 和 quote 均只保留“80000元”，实际仍接受并输出 exact/80000.00、无 reviewIssues。冻结 v3 会检查 value 在 quote 中、quote 在 block 中，但修饰词和群体诊断只读取模型选择的 quote 局部；字面存在本身不足以证明上下文完整。

最小修复是生产链路另加来源复核，按已验证来源哈希、block 及唯一引文位置定位金额，再从原始 block 展开有限事件上下文；直接附着的概数、上下界、符号、单位及同一局部群体线索不能依赖模型是否保留。重复 quote/value 不能默取第一处；跨句第三人、其他金额的概数也不能污染当前金额。原始回答和 quote 保留，只对派生金额降级并附核对问题。来源复核应覆盖新提取和历史 v2/v3 状态的读取、确认及计算路径，避免仅修新输入而旧个人候选继续可用。审查者没有编写该实现；独立模块、持久化整合及回归结果待实现后另记。

**P2：案件失效后，取消任务失败缺少可重试的任务凭据。** 审查者把当前 5 份真实数据库迁移加载到内存 SQLite，按路由原 SQL 执行 owned job SELECT 与归档 UPDATE：第一次能捕获已存在的任务 UUID，案件触发器随即删除 fact state；再次提交相同归档请求时 SELECT 已为空。当前数据库没有待清理任务记录，路由在 DELETE 超时后只返回 processingCleanupPending=true，下一请求不能重新找到该任务。这个复现没有向实际识别服务发送 DELETE；失败分支及重试不可达依据当前代码静态核查，数据库丢失任务关联则为实际执行结果。

现有 generation/CAS 仍阻止旧结果写回已失效案件，因此不应把取消失败扩大为旧事实恢复或越权。实质风险是已失去前端关联的后台任务继续占用资源，直至自身结束或超时；服务当前的 DELETE 对不存在任务也返回成功，具备重试所需的幂等行为。建议在同一数据库事务中于事实失效前保存 owned pending cancellation，事务提交后尝试取消，成功确认清理、失败保留；后续有权限的请求或明确重试动作再执行清理，同值/no-op PATCH 也应能重试。不能将待清理凭据放回会被触发器删除的事实行，也不应等待外部网络成功才撤销旧计算授权。

上述修复若采用独立生产来源 guard 和任务清理模块，均属于冻结后的产品修复。正式 v6 继续使用原冻结 v3、评分器和首次输出，不把生产 guard 的新增拒绝、降级或警告回灌 accepted 指标，也不据此声称模型提升。Qwen 仍排队等待原冻结协议运行；没有为复现或修复追加模型请求、训练或修改任何冻结文件。

### 先分清拒收原因，再判断语义

Qwen 正式 36 个拒收的首个拒绝理由是：15 个字段/条件形状无效、17 个引文不存在或未含 value、4 个主体/期间无字面支持。独立逐项查看原始对象确认：15 个形状错误都是 date 缺 subject 和 scope，其中 7 个还缺 rateUnit；它们的 period 实际均为 null，不能从通用拒绝说明里的“date.period 必须为 null”反推这 15 项都填错了 period。任某案 4 个不被原文支持的主体均写成笼统“班组”，原文写的是“13名农民工/13名被害人”，本轮不允许合成这个名称。

开发集 25 个拒收则是 22 个形状错误、2 个引文错误、1 个主体/期间错误。首案 15 个 date.completeness=unknown，981 案 6 个 date.completeness=complete，另有 1 个非 rate 却带 month 单位。它们违反明确的条件契约；首案把“任商务专员”“执行标准工时制”“某公司未提交相反证据”等无日期文本标成 date，则另外构成真实的事实类型错误。只修 completeness 不能使这些内容变成正确日期。

引文约束也不是任意阻拦正确答案。康某某 4 次签约的日期 value 和 contract_signing 角色本来正确，但 quote 都裁掉了日期；投资公司入职和解除的日期也有相同问题。Qwen 还在翁某案把“同月23日/同年12月26日”补成完整年份日期，在张某某案把引文的 30000 改成 30,000，在康某某案删掉金额内部原有空格。这些输出可能保留部分数值含义，但不符合原文字面证据契约，不能在本轮自动修复或当作新的首次回答。康某某 4 次签约同时还漏继承明确查明段的 decided，格式问题与 assertion 问题可以同时存在。

### 可以落实到原文的 Qwen 语义残差

- **欠款与完整应付混淆跨案出现。** 任某 30万余元、翁某 3.3万元、旅游公司 41万余元及鞋业 3 笔欠款均被写成 due_total；任某还标 complete。输入明确说拖欠，不能从欠款推出完整应付。张某某“约115万元工资全部支付完毕”又被写成 due_total/complete，并把付款人张某某写成 group 主体；这是已付与应付及受益方的明确错误，不是“约”字解析失败。该条仍为概数，程序没有把它变成精确值或 0。
- **收取方与承担人混淆。** 冯某案两笔罚金的 subject 分别写某信息公司、冯某，旅游案个人罚金写王某，均是罚金承担人；材料没有写收取机关，冻结标签因此是 null/unknown。任某工程款 910万余元和翁某售房款 50万元的收款人反而被漏成 null。这里有明确主体字段问题，但不把所有 basic 错误都归为主体错误。
- **群体当个人。** 翁某“洪某等3人”被标 individual，虽然 subject 已含“等3人”。冻结局部诊断实际给出 scope_text_mismatch，聚焦 raw/accepted 均明确计 1 个 group_as_individual。该条同时把 arrears 标 due_total，因此没有进入 basic TP；不能用 basic→relational 差值代替全部主体问题的计数。与 DeepSeek 相同名称但仍正确 group 的跨度问题应区别记录。
- **命令发生日不等于支付日。** 任某“同月29日……责令……足额支付”被标 payment_date、subject=任某，原文只给命令发生日期，没有给付款日期或截止日；与 DeepSeek 的同类错误一致。康某某签署结清证明的 2025年4月30日也被当 payment_date，材料明说约定 5月10号发放工资；签署凭据不能直接代表实际支付。

accepted basic→relational 的 7 个 TP 损失也应按实际配对解释：工程款收款人 1、两笔罚金承担人 2、售房款主体 1、旅游个人罚金主体 1，共 5 条主体/范围差异；鞋业另 1 条同额错事件且主体未知；康某某另 1 条期间缺失。relational→strict 只再损失 1 个 TP，是康某某解除劳动关系的 narrated/decided，不是又一个主体或金额错误。反过来，已经在 basic 因类型错误失配的群体个人问题，也不会显示在这 7 个差值里。

### 同额事件、别名与评分边界

鞋业的两个 105.7万元是本轮最清楚的评分局限。Qwen 在“为全体劳动者发放工资”的 quote 下输出 paid_total/complete，在“铝楦……予以变卖”的 quote 下输出 payment/partial，两者均 subject=null、scope=unknown。前者没有明确完整累计依据；后者其实是资产变卖金额，不能视为向劳动者支付。由于冻结 basic 只比较 kind/meaning/value，不比较该 quote 是否对应同一事件，资产变卖的 payment 恰好得到工资 payment 的 1 个 basic TP。relational 不匹配，聚焦诊断又因同额两角色保持 ambiguous，payment_as_paid_total 与 partial_as_complete_paid 没有强行计数。因此聚焦 complete 错误为 0 不代表这个具体错误不存在；本轮保留原分数，未来应在新协议增加事件证据对应的审查维度，不能事后把该 TP 改掉。
